SYSTEM ARCHITECTURE (4 LAYERS)
================================================================================

LAYER 1: INGESTION (PHASES 1, 2, 4, 8)
  When CSV/XLSX uploaded:
    1. Schema Discovery → Detect 18 semantic roles (quantity, revenue, date, etc)
    2. Persist Schema → Store mapping in Postgres StructuredFileSchema table
    3. Parallel Storage:
       - DuckDB: Raw rows (for aggregations)
       - Vector DB: Table-aware chunks (for semantic search)
       - Postgres: Schema metadata (for planning)

LAYER 2: QUERY PLANNING (PHASE 5)
  When user asks structured question:
    1. Detect operation (SUM/COUNT/AVG) from natural language
    2. Identify metric (QUANTITY/REVENUE/COST) requested
    3. Find compatible uploads (must have this metric)
    4. Return validated QueryPlan (JSON, not SQL)

LAYER 3: SQL COMPILATION (PHASE 6)
  Convert plan to safe, parameterized SQL:
    1. Resolve semantic → physical columns via resolver
    2. Generate UNION query for multi-file aggregation
    3. Apply date/value filters
    4. Output: parameterized SQL + params dict

LAYER 4: EXECUTION (PHASE 7)
  Run query and return with provenance:
    1. Execute via DuckDB (10-50ms for aggregations)
    2. Track which files contributed
    3. Return: {result, sources, provenance}

ROUTING AT QUERY TIME:
  User Query
    ↓
  [Is this structured?]
    ├─ YES → Layers 2-4 (DuckDB) → Result: 71 products
    ├─ NO → Existing semantic (unchanged) → Result: chunks
    └─ HYBRID → Both combined → Result: structured + context

DESIGN DECISIONS EXPLAINED
================================================================================

Decision 1: Schema Confidence Threshold (0.85)
  ✅ CHOSEN: 0.85
  ❌ REJECTED: 0.90 (too strict, miss valid columns)
  ❌ REJECTED: 0.75 (too loose, flag valid columns as ambiguous)
  → RATIONALE: Balance precision vs false negatives for ambiguous columns

Decision 2: Schema Versioning Strategy
  ✅ CHOSEN: New version on re-ingest, preserve old versions
  ❌ REJECTED: Delete old + merge (silent schema merges)
  ❌ REJECTED: No versioning (can't audit schema changes)
  → RATIONALE: Audit trail prevents silent schema changes

Decision 3: Column Mapping Approach
  ✅ CHOSEN: Single resolver function, called everywhere
  ❌ REJECTED: Inline logic in each module (duplication, hard to maintain)
  → RATIONALE: Centralized control, no inconsistencies

Decision 4: Ambiguous Column Handling
  ✅ CHOSEN: Flag but don't block ingestion
  ❌ REJECTED: Block ingestion (data lost, user frustrated)
  ❌ REJECTED: Guess mapping (silent errors, wrong numbers)
  → RATIONALE: User can resolve manually, data still available

Decision 5: Semantic Roles Design
  ✅ CHOSEN: 18-type Extensible Enum
  ❌ REJECTED: String-based (no type safety)
  ❌ REJECTED: Hardcoded list (can't add new roles)
  → RATIONALE: Type safety + extensibility

Decision 6: DuckDB Storage Approach
  ✅ CHOSEN: Global DB + kb_{id}_upload_{id} naming
  ❌ REJECTED: Per-KB database files (complexity vs scalability)
  → RATIONALE: Simplicity, single point of access

Decision 7: Query Plan Format
  ✅ CHOSEN: JSON-only plans, no SQL strings
  ❌ REJECTED: LLM generates SQL (injection risk, audit trail loss)
  → RATIONALE: Type safety, audit trail, prevents injection

Decision 8: Multi-File Aggregation
  ✅ CHOSEN: Column aliasing to canonical schema
  ❌ REJECTED: Separate queries then merge (atomicity loss)
  → RATIONALE: Single atomic query, correct semantics

Decision 9: Table Chunking Strategy
  ✅ CHOSEN: Preserve header, group by rows
  ❌ REJECTED: Character-count splitting (rows get split mid-record)
  → RATIONALE: Semantic search on tables still works
